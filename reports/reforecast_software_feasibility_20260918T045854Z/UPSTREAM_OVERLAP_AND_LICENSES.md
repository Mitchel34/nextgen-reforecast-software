# Upstream overlap, licenses, and packaging boundary

Checked 2026-09-18 UTC. This is a read-only source/documentation investigation, not a build, execution test, license selection, legal compatibility opinion, or priority claim. Public source text was fetched for inspection only; no upstream implementation or data was copied into the proposed project. The six-file outline repository can be published under the user's authorization without implying that the inherited runtime is ready for public software release. These are separate deliverables.

## Recommendation

Keep the proposed package thin: campaign/issue manifests, exact forcing-time/source bindings, qualified native-runtime selection, per-issue output commits, archive verification and history-replay planning. Reuse upstream domain preparation, forcing conversion, container execution and evaluation where their verified interfaces preserve the required semantics. Propose the minimum native state-boundary/provider/ownership hooks upstream; do not make another permanent complete engine fork. A DataStreamCLI extension or profile may be the better eventual home, subject to maintainer interest and a concrete interface comparison. No maintainers were contacted.

The potential distinctive contribution is a *demonstrated, bounded* shared-history/independent-branch/recovery contract. The inspected upstream tools already provide substantial workflow automation, forcing preparation, provenance recording and routing restart facilities. Their existence invalidates a broad claim that reproducible NextGen workflows or restart-based initialization are new. This review does not establish absence of an equivalent full contract anywhere upstream.

## Integration and maintenance backlog

1. **Retain:** issue/forcing/source identities and verified commit/archive interfaces; native source/preimage and binary/image identities. Keep generator scope separate from correction experiments. Local examples are `shared_history_recovery_v2.py:seal_branch_commit` (70), `verify_commit` (164), `recovery_plan` (198), and `shared_history_day_shard_v1.py:create_day_shard` (178), `recovery_schedule` (248), under the deployed logical source root above. Their presence is source evidence; test outcomes belong in the dedicated evidence report.
2. **Refactor after authorization:** replace author paths with explicit campaign/runtime/asset interfaces; create install metadata and a minimal dependency set; isolate cloud custody and independent routing adapters. Require schema/source-preservation tests before substituting upstream processors. Relative burden: medium for packaging; potentially high for semantic adapter qualification.
3. **Propose upstream:** maintain a minimal, pinned engine patch series or sanctioned hook; share the exact boundary, handle-reopening, clock, output-ownership and failure tests with engine maintainers. Relative burden: high and maintainer-dependent; no timeline inferred.
4. **Resolve before software release:** contributor rights/license, versioned notices, binary/component attestations, exact middleware loading, fully retained initialization assets and example data rights. Documentation publication does not resolve these.
5. **Defer:** broad realization/MPI/platform support and generic evaluation/domain GUI features. Publish only the platform/component profile supported by matched runtime receipts. Use the extraction dossier to choose between an independent thin package and a maintained upstream workflow profile.
