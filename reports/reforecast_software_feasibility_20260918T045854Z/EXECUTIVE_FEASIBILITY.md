# NextGen reforecast software feasibility

**Decision: proceed toward a narrow, state-aware software extraction, with the current milestone limited to this evidence dossier.** The existing kernel has credible inspected source and historical qualification/production receipts. A complete, independently runnable and redistributable public package is not yet established. Publishing this design repository does not establish a software release, a new model result, or a validated new build.

## What was completed

The original six-file software/manuscript outline was preserved as `nextgen_Software/` in the separate public `Mitchel34/nextgen-reforecast-software` repository under the owner's explicit instruction. The supplied investigation prompt was followed through its stop condition: source/version, state/recovery, data/example, licensing/upstream and benchmark findings, plus a prioritized backlog. No original research code or data was copied into the public repository. Original Reforecast/HYDRA workspaces were used only for read-only evidence inspection.

## Consequential verified findings

1. **The contribution is inside the runtime, not just scheduling.** The actual V3 source performs live same-host process branching, independently reopens input handles, creates child-owned routing and waits for isolation before advancing history. At issue I, history has consumed intervals [origin,I); branches use interval starts I through I+17h and predict targets I+1h through I+18h. Evidence: `STATE_AND_RECOVERY.md`, `N/include/shared_history/Runtime.hpp:407–460,484–549`, and the exact source/build identities in `SOURCE_VERSION_MAP.json`.
2. **Recovery is history replay.** Land state is inherited in process memory; channel q0/clock can be serialized, but daily output archives explicitly say `state_checkpoint:false`. Reusing valid commits can suppress completed forecast issues while historical reconstruction still begins at the same origin. A recovery helper is implemented, but production-scale parent/host-loss replay equivalence is not established by the inspected receipts. Evidence: `C/src/nextgen_reforecast/shared_history_recovery_v2.py:164–231`, `shared_history_day_shard_v1.py:178–241`, and `STATE_AND_RECOVERY.md`.
3. **Version boundaries matter.** The two-domain weekly comparison uses native hash `f4d4690c…`; the V3 day-custody qualification and final production use `ee65c774…`. The V3 local receipt supports Watauga, 786 history hours, two branches and output-cursor/custody recovery; it does not supply a complete land restart. The weekly comparison reports 9,072 keyed rows within abs=1e-6/rel=1e-5, with some nonzero differences, and changes CPU allocations. Evidence: `benchmark_receipts.json` and `BENCHMARK_EVIDENCE_AND_PLAN.md`.
4. **Reuse is initially a narrow scientific profile.** Production source binds Watauga (31 catchments) and New River (393 catchments, two nested gauge outputs), SLOTH/NoahOWP/CFE, hourly 18-hour branches and restricted channel routing. Arbitrary basins, horizons, realizations and routing modes require refactoring and qualification. Forcing semantics include next-label AORC precipitation conversion, exact NWM issue/lead selection, explicit retrospective gap treatment and unresolved shortwave timing. Evidence: `DATA_AND_CONFIGURATION.md` and its source references.
5. **The smallest real example is incomplete.** The existing Watauga V3 qualification fixture has 181 files: 49 resident files totaling 906,503 bytes and 132 dataless placeholders. Its contract and much of its forcing are unavailable locally without restoration. Separate production history files are resident by metadata but have a different origin and cannot silently replace that fixture's initialization. Source-cache runtime hashes were checked, but a complete redistributable example and its total byte size remain unverified. Evidence: `MINIMAL_EXAMPLE_MANIFEST.json`, `forcing_checks.json`.
6. **Public packaging has unresolved ownership and provenance work.** The framework pin and exact V3 headers/build export are recoverable; not every physical component binary is attested to its source. The exact middleware and its loading path matter. Upstream tools already provide forcing, execution, provenance and routing-restart interfaces. Their licenses and data terms have distinct scopes; no project-wide license was selected. Evidence: `UPSTREAM_OVERLAP_AND_LICENSES.md`, which pins six current official repositories and links exact source files.

## Recommended boundary

Extract a thin package for campaign and issue manifests, exact forcing/time bindings, a version-qualified native adapter, committed-output verification, archive export and explicit history-replay planning. Reuse upstream domain, forcing and execution infrastructure where conformance tests show that the scientific contract is preserved. Propose a minimal native hook/patch upstream rather than maintaining an entire permanent engine fork. A DataStreamCLI extension/profile remains an alternative pending maintainer discussion; no upstream agreement or novelty priority is claimed.

The next concrete engineering milestone is a reproducible V3 build plus one sealed complete Watauga fixture, followed by a clean-environment reference comparison. `EXTRACTION_BACKLOG.md` gives dependencies and relative effort. `BENCHMARK_EVIDENCE_AND_PLAN.md` defines the smallest subsequent reliability, equal-resource performance, two-domain and independent-user study. No benchmark plan was executed during this investigation.

## Decisions and missing evidence for the owner or maintainers

- Establish original-code contributors and rights, then choose a license after dependency and data/example scope is resolved.
- Restore the exact missing qualification inputs/contract and confirm a durable distribution location and data terms. Preserve its original initialization rather than substituting a differently initialized production history.
- Select a maintained native integration boundary with engine maintainers and resolve the binary/component/middleware build attestations.
- Choose whether the initial deliverable is a separate thin package or an upstream workflow profile after comparing concrete interfaces. Do not infer community naming approval from this repository's existence.
- Scope future build/model/recovery experiments separately. This dossier does not launch them or request infrastructure.
