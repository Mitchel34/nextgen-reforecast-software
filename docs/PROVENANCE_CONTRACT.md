# Planning provenance foundation — RF-003

`planning-lock/0.1` is an offline snapshot of a normalized campaign, its domain identities and explicitly declared metadata. It is not the future execution-ready scientific lock described by RF-003/RF-007. Creating it requires every campaign asset role, size and SHA-256 to pass resident-file checks. The existing no-follow, no-hydration and bounded-read rules apply.

The Python API provides `seal_lock(spec, base_dir, evidence=None)`, `load_lock(path)` and `verify_lock(lock, base_dir)`. CLI `lock` creates a new snapshot without overwriting a destination; `verify-lock --asset-root` checks it against an explicitly chosen asset directory. Assets stay relative to that directory, not the location where a lock has been copied. CLI creation binds normalized campaign values, rather than the original JSON whitespace/key order, with all scientific evidence fields null; adapters may supply metadata using the Python API. Neither operation downloads inputs.

Six metadata categories are required and default to JSON null: `runtime`, `source_objects`, `transformations`, `gap_policy`, `scientific_configuration` and `output_schema`. A supplied nonempty object is recorded as **declared, unvalidated**. Its contents are hashed without assuming they are complete, scientifically correct or authoritative. Unknown source releases are not inferred. Later admission validators must validate source timestamps/intervals/units, component artifacts, configuration semantics, gaps, output and rights against typed contracts before execution.

The experiment identity hashes the normalized campaign plus metadata. Per-domain identities hash shared campaign fields, that domain and metadata, preserving the domain/location/asset axis. Changed origin, issue schedule, retention, resources, source metadata, treatment, configuration or bound asset changes identity. Schema 1.1 schedule shorthand is expanded before hashing. Projection occurs at export and never removes required runtime completion evidence. The snapshot digest is a consistency checksum, not a cryptographic signature or independent proof of source truth.

`verify_lock` first checks the entire structure, fixed evidence-boundary fields and identities, then freshly verifies resident assets. Changed/missing bytes make `input_bytes_verified` false; metadata tampering raises an error. It always reports `execution_ready: false` and `scientific_semantics_verified: false`. A successful CLI exit means the requested offline identity operation succeeded. It never means a simulation ran or can run. Verification is a point-in-time inspection; a future executor must re-admit inputs at use time and bind actual loaded artifacts and output receipts.

Bounds: 4 MiB normalized campaign, 1 MiB metadata, 8 MiB lock file, plus the existing per-asset and total hashing limits. Duplicate keys, nonfinite JSON, unsafe file paths, symlinks, placeholders, missing roles and mismatched bytes fail. Publication is atomic and refuses existing destinations.

Still required for full RF-003: typed source/transform/parameter/runtime admission, decoded forcing payload evidence, physical interval and catchment-axis validation, event provenance for preparation/execution/replay/publication, and output custody checked against the same scientific identity. Synthetic lock tests establish identity mechanics only.
